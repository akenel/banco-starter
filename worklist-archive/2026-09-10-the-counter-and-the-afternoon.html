The one that should change how we test

The five-rappen cash rounding had never run. On any machine. Since the day it was written.

Checkout said Total Due 27.96 · Change 2.04. The receipt said 27.95 / 2.05, and so did the drawer. The cashier was being told to count out a coin that has not existed since 2007.

  • The server sends cash_rounding_step: '0.05' inside the regime object.
  • base.html lifted two fields out of that object and dropped the rest, leaving POSConfig.regime as the string 'CH'.
  • checkout.cashRoundStep() read POSConfig.regime.cash_rounding_step → 'CH'.cash_rounding_step → undefined → step 0 → never rounded.

It has 2,009 passing test cases. They inject {regime: {cash_rounding_step: '0.05'}} — an object production has never produced. The fixture could not fail the way production fails, so it never did. Point it at the real shape and the old code fails on the first case: "till shows 0.01, server charges 0.00."

Only a percentage discount can make a total that isn't a multiple of five rappen — every shelf price already is. Four months of testing never produced one. A sheet built on purpose to land on 27.96 caught it on the first run.

New idea — the box code

Angel, 2026-09-10, on filters: "they have a lot of filters there, different types, Bob Marley filters and stuff, and there's a scan code on the back of it, and it picked that up, but that was for the box of them."

The packet a customer buys has no code of its own; the code on the shelf is the outer box. So a scan resolves to a box of N and the shop sells singles. The shape of a fix: bind the box code, record how many singles are in it, and let the till break the box down — scan the box, sell one. His own caveat: "maybe there's a box, and it's also a single or something, but that's a problem... it's very rare, I guess. It's more of filters. He sells a lot of filters."

Not built, not designed. Written down so it survives the night.

What today should teach us

  • A test that checks totals cannot see an unreadable total. Nine green proof sections, 2,378 passing tests, and the thing a person could not read was invisible to all of them. The new checks ask what a person can verify: does the row multiply out, does the column close, does one word mean one number.
  • A fixture that cannot fail the way production fails is not a fixture. The rounding had 2,009 cases and a shape production never produces. Twice more the same day: I "found" a treat/deal bug with a cart line the app never builds, and got product_class: 'tobacco' wrong when the real value is tobacco_nicotine. Both times the fixture lied, not the code.
  • A locator that walks a layout breaks when the layout moves. Three in one afternoon — "the span after the TOTAL", "the div after the TOTAL", "the last child of the enclosing div". Ask for the thing by its label.
  • A harness that goes red for reasons unrelated to its subject teaches you to ignore it. A flat 3.5-second sleep after Login meant a cold Keycloak reported five pricing failures.
  • The design that lives at the counter is in no comment. I priced four shelf separators as broken data. They are a deliberate intake aid. Grepping the code found nothing because the reason was in Angel's hands, not in the repo.
