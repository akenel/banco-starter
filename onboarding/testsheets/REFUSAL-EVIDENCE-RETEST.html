What this is. The full 27-step sheet (AGE-EVIDENCE-TESTSHEET.html) is done — you ran it on 2026-08-12 and it found two things the machine probe could not. This sheet retests one of them: commit efbc056, "a refusal was filed against the NEXT customer's sale". Everything else on that sheet stays passed; do not re-run it.
The defect, in one paragraph. Both sale paths stamped the refusal with TXN-{today}-{count+1} — a number derived by counting committed transactions. A refusal raises a 400 and never commits, so it never consumes its number. The next customer's sale takes it. Measured on this database: 17 of 52 refusals "belong" to a completed sale, and 7 of those sales have no 18+ line at all. A compliance record pointing at the wrong transaction is worse than no record — it is a document that lies under its own letterhead.
The fix. A refusal's txn_ref is now NULL on the /sales path — on purpose, because at refusal time no transaction exists. What identifies a refusal is the thing it is actually about: the cart attempt. New column age_check_event.cart_ref carries the checkout screen's client_uuid, which joins to transactions.client_uuid. So a customer who is refused and then cleared properly leaves both rows on one thread — and a customer who walks out leaves a refusal that points at no sale, which is the truth.
The checkout path still fills txn_ref, because there a transaction genuinely already exists.
⛔ Sandbox only. You will ring real completed sales. A completed transaction is a line in the Kassenbuch. Never run this against the shop's books. Evidence rows are append-only by design and cannot be cleaned up — that is the feature working, and it is also why Part L exists.

Part R — The retest · v2, rewritten 2026-08-13 after the first run

R · The till has TWO refusals, and only one of them reaches the server

⚠️ v1 of this sheet was wrong and cost you 14 minutes. Here is what it got wrong. R1 said "decline the cashier attestation at the 🔞 popup" and expected a refusal row. But the popup's decline button is "🚫 Refuse — remove 18+ item(s)", and that button is pure client-side JavaScript (checkout.html:1048): it strips the 18+ line out of the cart, closes the modal, and never calls the server. Nothing is refused, because nothing was ever asked. Your remaining items then completed normally — which is exactly what your TXN-20260813-0001 receipt shows.
Proof, from the app log across your whole run: three POST /api/v1/pos/sales, all 201 Created. Not one 400. The browser never asked the server to refuse anything, so there was nothing for the evidence table to record. Your 0-row results were correct readings of a test that never happened.
So which button DOES reach the server? completeTransaction() checks needsAgeGate() and returns before the POST whenever the cart holds an 18+ line with no of-age member and no attestation. The client mirrors the server, so the client wins first and the server is never troubled. The one path that gets through is the one where the client and server disagree: a member proven under 18 by DOB, plus a cashier attestation. The client lets it go (the cashier attested); the server refuses (the DOB is authoritative). That is R2.

Log in at http://localhost:3000/pos as pam / pam — a cashier, not an admin. The 18+ product is CBD Gummy — type gummy in the search box and it is the only hit (verified over the API: is_age_restricted: true, age_total: 1). Nothing has a barcode — type the name, do not reach for the gun. Pay by TWINT to skip the cash-drawer requirement. Check the cart is empty before each step — your three receipts each carried the previous one's items along.
