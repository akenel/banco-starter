The receipt QR points at the shop

Today every receipt carries a “Come find us on La Piazza” QR that is fetched from a third-party image service and points at a Banco permalink. It should carry the shop’s own invite, point at the shop’s own website, take that address from Store Settings — and be drawn by Banco, so a receipt still prints when the wifi is down.

Written 4 Sep 2026 Screen receipt, every sale Files receipt.html · pos_router.py · pos-i18n.js Blocks go-live? no — but it prints on every receipt from day one

So the current chain is receipt → api.qrserver.com → /join → 302 → La Piazza. The /join route is pos_router.py:13148, banco_join_lapiazza.

The TODO is the real finding. It says the image service “is fine for the test.” It is no longer a test. A receipt whose QR is fetched from someone else’s server fails in three ways at a counter: it is a broken image box the moment the shop’s wifi drops — the exact scenario the service worker and the IndexedDB catalogue mirror were built to survive; it sends every render to a third party, which is off-message for a product sold on you own this; and when that service is slow, the hole in the receipt appears with a customer standing there.

2 · The decision

and why, so it is not re-argued

Destination: the shop’s own website, directly — not through /join

Keeping the Banco-owned redirect was tempting, because a printed QR is permanent and a redirect you own can be repointed without reprinting. It loses on one thing: a phone shows the URL before the customer taps it. A caption that names artemisluzern.ch over a preview reading banco.wolfhold.app/join looks like a redirect someone should not trust. Print and preview must agree. (If the community funnel later matters more than that, the fallback path below already keeps /join alive and this can be reversed in one line.)

Caption follows the destination

If it lands on the shop’s site, “Come find us on La Piazza” is describing somewhere else. New copy, all four locales:

receipt.site_title   Kräuter & Düfte seit 1999
receipt.site_sub     Scan to visit us at artemisluzern.ch

The sub-line should render the host from settings, not a hardcoded string — otherwise the next shop prints Artemis’ domain under their own QR.

The address comes from Store Settings

store_settings.website already exists — src/db/models/store_settings_model.py:119, “Store website URL” — and is editable at Settings → Contact & Links. It currently holds artemisluzern.ch. Do not hardcode the domain in the template. This is the starter; the next shop is not Artemis, and a customer’s domain baked into a template is what turns a starter into a one-customer fork.

3 · Normalising the address

the part that fails silently
The stored value has no scheme. The setting is artemisluzern.ch. A QR containing a bare hostname is not reliably treated as a URL — some scanner apps show it as plain text with nothing to tap. Encoding the field as-is produces a QR that scans, looks fine, and does nothing. Normalise before encoding.

Measured 4 Sep 2026, so the canonical form is not a guess:

requestedresult
https://artemisluzern.ch301 → https://www.artemisluzern.ch/
http://artemisluzern.ch301 → https://www.artemisluzern.ch/
https://www.artemisluzern.ch200 ✓ canonical

Rules:

  • No scheme → prepend https://. Never http://.
  • Encode the address that answers 200 without redirecting — here the www form. One less round trip for someone scanning on a weak signal outside the shop.
  • Trim whitespace and a trailing slash before comparing; store what the shop typed, encode what resolves.
  • Anything that is not a plausible host after normalising → treat as unset (see the fallback).

The fallback is what keeps the starter honest: a shop that clones Banco and has not filled in a website gets the community invite rather than a dead QR, and a shop that has one never prints somebody else’s.

5 · Drawing the QR

the answer already exists
Do not vendor a JS library and do not add an endpoint. _qr_data_uri(payload, logo_url) — pos_router.py, just above /pos/products/{id}/label — already renders a QR PNG as a data URI, server-side, using the qrcode package that is already in requirements.txt. It picks ERROR_CORRECT_H when there is a logo to punch through and M when there is not, and it returns "" rather than raising, because a label with no code still beats a 500 at the counter. It is measured against both of the shop’s guns, 2026-07-29, readable down to 10mm.

Reuse it. A data URI is the right shape here for the same reason it was right for the label: no network at print time, no third party, no latency, and it survives the offline case the service worker exists to cover.

One thing for the implementer to confirm: joinQrUrl() is an Alpine method, so the receipt builds this client-side. The QR content is stable — it only changes when Store Settings change — so the cleanest wiring is for the server to hand the finished data URI down in the same store-settings payload the receipt already loads (alongside address_line1, city and the rest), rather than adding a fetch that would reintroduce the network dependency this change exists to remove.

6 · Copy, in four languages

or a Romandie prospect notices

The strings are i18n keys — receipt.lapiazza_title and receipt.lapiazza_sub in src/static/pos/pos-i18n.js. New keys need DE, FR, IT and EN, and the old keys stay, because the fallback path still uses them.

This repo has shipped an English value inside the FR locale before — "8:00 AM" in closeout.html, while DE and IT already said 8:00. The receipt is the one piece of Banco a customer takes home, and four working languages is a sales asset worth protecting. Check all four, not the two you read.

Falls back to /join with the La Piazza copy. No dead QR, no empty box.

What the print stylesheet does with the “PAID” watermark
It is large and diagonal on screen. On thermal it either drops or eats ink. Look once while the receipt is open anyway.

8 · Out of scope

so it does not grow
  • Tracking. A ?utm_source=receipt would tell the shop whether anyone ever scans it. Worth deciding later; it lengthens the payload trivially and changes nothing structural.
  • Per-transaction codes. The current design is deliberately a one-way funnel with no tie-back to the POS. Leave it that way.
  • Facebook and Instagram. Both fields exist and are empty. One QR, not three.
  • The Payment Method: VISA line. The receipt, the Z-report and the Banana CSV all read the same field, so it moves with the Cash/Card/TWINT decision — not with this.
